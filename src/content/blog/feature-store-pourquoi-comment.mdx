Une feature calculée d'une manière en entraînement (un batch Python sur un historique complet)
et d'une autre en production (un calcul en temps réel sur un event unique) produit, tôt ou
tard, des résultats différents pour la même définition logique. Ce décalage, le
*training-serving skew*, est l'un des bugs les plus difficiles à diagnostiquer en Machine
Learning — le modèle fonctionne, les métriques semblent correctes, mais les prédictions en
production divergent silencieusement de ce qui a été validé hors ligne.

## Le problème que résout un feature store

Un feature store centralise la définition et le calcul des features pour qu'elles soient
identiques, qu'on les consomme :

- **Hors ligne (offline store)** — pour l'entraînement, sur de gros volumes historiques,
  généralement dans un data warehouse ou un data lake.
- **En ligne (online store)** — pour l'inférence en temps réel, avec une latence de quelques
  millisecondes, typiquement dans une base clé-valeur (Redis, DynamoDB).

La définition de la feature est écrite une seule fois ; le feature store se charge de la
matérialiser dans les deux environnements de façon cohérente.

## Un exemple avec Feast

```python
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Entraînement : récupération historique pour un jeu de données de features
features_entrainement = store.get_historical_features(
    entity_df=entity_df,
    features=["client_stats:frequence_sinistres_12m", "client_stats:anciennete"],
).to_df()

# Production : récupération en temps réel pour une seule entité
features_temps_reel = store.get_online_features(
    features=["client_stats:frequence_sinistres_12m", "client_stats:anciennete"],
    entity_rows=[{"client_id": 4821}],
).to_dict()
```

Même définition de feature, deux modes de récupération — c'est exactement ce qui élimine le
risque de divergence entre entraînement et production.

## Le bénéfice secondaire : la réutilisation

Au-delà de la cohérence, un feature store évite qu'une même feature ("fréquence de sinistres
sur 12 mois") soit recalculée avec de légères variations par trois équipes différentes. Chaque
équipe consomme la même définition versionnée, ce qui simplifie aussi l'audit et la
gouvernance des données utilisées par les modèles.

## Quand c'est probablement excessif

Un feature store ajoute une infrastructure et une complexité opérationnelle réelles. Pour une
équipe avec un ou deux modèles en production et peu de features partagées, un pipeline batch
classique bien documenté suffit largement. Le feature store devient pertinent à partir du
moment où plusieurs modèles et plusieurs équipes consomment les mêmes features, et que le coût
des incohérences dépasse celui de l'infrastructure supplémentaire.
