Une feature calculée d'une façon en entraînement — un batch Python sur un historique complet —
et d'une autre en production — un calcul en temps réel sur un event unique — finit tôt ou tard
par produire des résultats différents pour la même définition logique. Ce décalage, le
*training-serving skew*, est vicieux : le modèle fonctionne, les métriques hors ligne semblent
correctes, mais les prédictions en production divergent silencieusement de ce qui a été
validé.

## Ce qu'un feature store règle

Il centralise la définition et le calcul des features pour qu'elles soient identiques, qu'on
les consomme hors ligne — pour l'entraînement, sur de gros volumes historiques, généralement
dans un data warehouse ou un data lake — ou en ligne, pour l'inférence en temps réel avec une
latence de quelques millisecondes, typiquement dans une base clé-valeur comme Redis ou
DynamoDB. La définition s'écrit une seule fois, le feature store se charge de la matérialiser
dans les deux environnements de façon cohérente.

```python
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Entraînement
features_entrainement = store.get_historical_features(
    entity_df=entity_df,
    features=["client_stats:frequence_sinistres_12m", "client_stats:anciennete"],
).to_df()

# Production, en temps réel pour une seule entité
features_temps_reel = store.get_online_features(
    features=["client_stats:frequence_sinistres_12m", "client_stats:anciennete"],
    entity_rows=[{"client_id": 4821}],
).to_dict()
```

Même définition, deux modes de récupération — exactement ce qui élimine le risque de
divergence.

Au-delà de la cohérence, il y a un bénéfice moins visible mais tout aussi réel : éviter qu'une
même feature soit recalculée avec de légères variations par trois équipes différentes, ce qui
simplifie l'audit et la gouvernance des données utilisées par les modèles.

Cela dit, un feature store ajoute une infrastructure et une complexité opérationnelle réelles.
Pour une équipe avec un ou deux modèles en production et peu de features partagées, un pipeline
batch classique bien documenté suffit largement — le feature store ne devient vraiment
pertinent qu'à partir du moment où plusieurs modèles et plusieurs équipes consomment les mêmes
features, et que le coût des incohérences dépasse celui de l'infrastructure supplémentaire.
