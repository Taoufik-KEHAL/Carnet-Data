Un bon score sur un notebook Jupyter ne dit encore rien de la capacité d'un modèle à tourner en
production. C'est souvent la première leçon qu'on apprend à ses dépens sur ce métier : l'écart
entre "ça marche sur mon poste" et "ça tourne de façon fiable pour de vrais utilisateurs" est
énorme, et c'est exactement ce que le MLOps essaie de combler.

Le MLOps applique les principes du DevOps au cycle de vie des modèles de Machine Learning :
versionnement, tests automatisés, déploiement continu, monitoring. La différence avec le
DevOps classique, c'est qu'on ne versionne pas seulement du code, mais aussi des données et des
modèles, dont le comportement peut dériver dans le temps sans qu'une seule ligne de code n'ait
changé.

Un pipeline minimal tient sur trois piliers. Le versionnement d'abord : du code avec Git, des
données avec DVC ou un simple système de hachage, des modèles via un outil comme MLflow Model
Registry. L'automatisation ensuite, un pipeline CI/CD qui entraîne, teste et déploie sans
intervention manuelle à chaque étape. Et le monitoring, qui doit suivre non seulement la
disponibilité du service mais aussi la qualité des prédictions et la dérive des données une
fois en production.

Pas besoin d'une infrastructure Kubernetes complexe pour démarrer. Un pipeline viable ressemble
souvent à ça :

```python
# entraînement.py — versionné avec le code
import mlflow

with mlflow.start_run():
    model = train(X_train, y_train)
    mlflow.log_metric("f1_score", evaluate(model, X_test, y_test))
    mlflow.sklearn.log_model(model, "modele")
```

L'objectif n'est pas la sophistication, c'est la traçabilité : pouvoir répondre à "quelle
version du modèle a produit cette prédiction, avec quelles données" à n'importe quel moment,
pas seulement le jour du déploiement.

La suite logique, une fois ce socle en place, c'est d'automatiser tout ça dans un vrai pipeline
CI/CD — ce sera le sujet d'une prochaine entrée.
