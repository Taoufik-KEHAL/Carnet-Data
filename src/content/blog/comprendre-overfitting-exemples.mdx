"Le modèle overfitte" est souvent dit sans qu'on visualise vraiment ce que ça implique. Un
exemple simple, avec une régression polynomiale, rend le phénomène concret plutôt
qu'abstrait.

## Un exemple minimal

```python
import numpy as np
from sklearn.preprocessing import PolynomialFeatures
from sklearn.linear_model import LinearRegression
from sklearn.metrics import mean_squared_error

for degre in [1, 3, 15]:
    poly = PolynomialFeatures(degree=degre)
    X_train_poly = poly.fit_transform(X_train)
    X_test_poly = poly.transform(X_test)

    model = LinearRegression().fit(X_train_poly, y_train)
    erreur_train = mean_squared_error(y_train, model.predict(X_train_poly))
    erreur_test = mean_squared_error(y_test, model.predict(X_test_poly))

    print(f"degré {degre} — train: {erreur_train:.3f}, test: {erreur_test:.3f}")
```

Avec un degré 1, les deux erreurs sont proches mais élevées (sous-apprentissage). Avec un
degré 15, l'erreur d'entraînement s'effondre presque à zéro — le modèle passe par quasiment
tous les points d'entraînement — mais l'erreur de test explose. Le modèle n'a pas appris la
tendance sous-jacente, il a mémorisé le bruit spécifique à l'échantillon d'entraînement.

## Le symptôme à surveiller

Le signal le plus fiable d'overfitting n'est pas "le modèle a une erreur d'entraînement basse"
— c'est **l'écart** entre erreur d'entraînement et erreur de test. Un petit écart avec une
erreur de test acceptable est sain. Un grand écart, même si l'erreur de test reste correcte
dans l'absolu, signale un modèle fragile qui généralisera mal à des données légèrement
différentes de celles vues en entraînement.

## Pourquoi ça arrive en pratique

- **Trop de paramètres pour trop peu de données** — un modèle avec une grande capacité
  (arbres profonds, réseaux de neurones larges, polynômes de haut degré) peut s'ajuster au
  bruit si le jeu de données est petit.
- **Fuite d'information (*data leakage*)** — une feature calculée à partir d'informations qui
  ne seraient pas disponibles au moment de la prédiction réelle donne une performance test
  artificiellement élevée, qui s'effondre en production.
- **Validation croisée absente ou mal faite** — évaluer sur un seul split train/test peut
  masquer une variance importante que la validation croisée (k-fold) révélerait.

## Les leviers pour corriger

Réduire la capacité du modèle (moins de profondeur, moins de features), ajouter de la
régularisation (L1/L2, `max_depth` limité, *early stopping*), ou simplement collecter plus de
données. Aucune de ces solutions n'est universelle : le bon réflexe est de toujours comparer
erreur d'entraînement et erreur de validation avant de juger un modèle "performant".
