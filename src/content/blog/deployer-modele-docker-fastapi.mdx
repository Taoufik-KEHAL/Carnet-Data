FastAPI pour l'API, Docker pour l'empaqueter — c'est le montage le plus rapide pour sortir un
modèle du notebook et le rendre appelable par un autre service. Pas besoin d'orchestrateur
complexe pour un premier déploiement.

```python
# app.py
from fastapi import FastAPI
import joblib
import pandas as pd

app = FastAPI()
model = joblib.load("modele.pkl")

@app.post("/predict")
def predict(features: dict):
    X = pd.DataFrame([features])
    proba = model.predict_proba(X)[0][1]
    return {"probabilite": round(float(proba), 4)}

@app.get("/health")
def health():
    return {"status": "ok"}
```

L'endpoint `/health` n'est pas décoratif. C'est ce que l'orchestrateur ou le load balancer
interroge pour savoir si l'instance peut recevoir du trafic — l'oublier fait souvent perdre une
soirée de débogage plus tard.

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY modele.pkl app.py .

CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

Le vrai bénéfice du conteneur n'est pas le déploiement en soi, c'est la garantie que
scikit-learn et pandas tournent en production exactement dans les versions utilisées à
l'entraînement. Un écart de version mineur peut changer silencieusement le comportement d'un
modèle — j'ai vu une différence de version de scikit-learn faire varier une probabilité de
prédiction de plusieurs points, sans erreur, sans warning.

```bash
docker build -t scoring-api .
docker run -p 8000:8000 scoring-api

curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"age": 34, "revenu": 42000, "anciennete": 5}'
```

Cette approche tient bien pour un trafic modéré. Au-delà, ou pour du scaling automatique, il
faudra ajouter Kubernetes et probablement séparer le chargement du modèle du cycle de vie de
l'API, via un serveur dédié comme BentoML ou Triton. Mais pour une première mise en prod ou une
API interne à faible trafic, ça suffit largement.
