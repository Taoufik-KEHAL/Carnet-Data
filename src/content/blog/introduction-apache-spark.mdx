## Le changement de modèle mental

Spark ne se contente pas de paralléliser pandas. Deux différences structurent tout le reste :

- **Évaluation paresseuse (*lazy evaluation*)** — les transformations (`filter`, `select`,
  `groupBy`) ne s'exécutent pas immédiatement. Spark construit un plan d'exécution et ne le
  déclenche qu'à une action (`show`, `collect`, `write`).
- **Distribution des données** — un DataFrame Spark est partitionné entre plusieurs exécuteurs,
  potentiellement sur plusieurs machines. Le code ressemble à du pandas, mais s'exécute
  différemment.

## Un exemple simple

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, avg

spark = SparkSession.builder.appName("exploration").getOrCreate()

df = spark.read.parquet("s3://bucket/transactions/")

resultat = (
    df.filter(col("montant") > 0)
      .groupBy("categorie")
      .agg(avg("montant").alias("montant_moyen"))
)

resultat.show()  # déclenche réellement le calcul
```

Rien de tout cela ne s'exécute avant `.show()` — `filter`, `groupBy` et `agg` ne font que
décrire le plan.

## Les erreurs classiques d'un profil pandas

- **Appeler `.collect()` trop tôt** — cela rapatrie l'intégralité du résultat sur le driver,
  annulant l'intérêt de la distribution si le volume est important.
- **Ignorer le partitionnement** — un mauvais partitionnement (trop de petites partitions, ou
  une seule énorme) dégrade fortement les performances, même avec un cluster correctement
  dimensionné.
- **Traiter Spark comme pandas ligne par ligne** — les UDF Python (`udf()`) cassent
  l'optimisation interne de Spark ; privilégier les fonctions natives (`pyspark.sql.functions`)
  chaque fois que possible.

## Faut-il vraiment migrer ?

Spark a un coût : complexité opérationnelle, temps de démarrage du cluster, débogage plus
difficile qu'un `print()` dans un notebook. En dessous de quelques dizaines de gigaoctets, des
outils comme DuckDB ou Polars offrent souvent un meilleur rapport simplicité/performance.
Spark devient pertinent quand les données dépassent la mémoire d'une seule machine ou que le
pipeline doit tourner régulièrement sur un cluster déjà en place.
