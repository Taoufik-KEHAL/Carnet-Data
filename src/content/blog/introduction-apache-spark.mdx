La question ne devrait presque jamais être "pandas ou Spark" mais "à partir de quel volume
pandas commence à souffrir". Tant que les données tiennent en mémoire sur une machine, pandas
reste plus simple et souvent plus rapide. Le jour où ce n'est plus le cas, Spark répond à un
problème différent : distribuer le calcul sur plusieurs machines.

## Deux réflexes à changer

Premier réflexe à perdre : Spark n'exécute rien tout de suite. Les transformations comme
`filter`, `select` ou `groupBy` construisent un plan d'exécution, qui n'est déclenché qu'à une
action comme `show()` ou `write()`. Deuxième réflexe à changer : les données sont partitionnées
entre plusieurs exécuteurs, potentiellement sur plusieurs machines, alors que le code
ressemble beaucoup à du pandas classique.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, avg

spark = SparkSession.builder.appName("exploration").getOrCreate()
df = spark.read.parquet("s3://bucket/transactions/")

resultat = (
    df.filter(col("montant") > 0)
      .groupBy("categorie")
      .agg(avg("montant").alias("montant_moyen"))
)

resultat.show()  # rien ne s'est exécuté avant cette ligne
```

## Les erreurs qu'on importe de pandas sans le vouloir

Appeler `.collect()` trop tôt rapatrie tout le résultat sur le driver et annule l'intérêt de
la distribution. Ignorer le partitionnement — trop de petites partitions, ou une seule énorme —
dégrade les performances même sur un cluster bien dimensionné. Et écrire des UDF Python pour
traiter les lignes une par une casse l'optimisation interne de Spark ; les fonctions natives de
`pyspark.sql.functions` couvrent la grande majorité des besoins sans ce coût.

Spark a un vrai coût opérationnel : complexité de cluster, temps de démarrage, un débogage
nettement moins confortable qu'un `print()` dans un notebook. En dessous de quelques dizaines
de gigaoctets, DuckDB ou Polars donnent souvent un meilleur rapport simplicité/performance.
Spark devient pertinent quand les données dépassent la mémoire d'une seule machine, ou que le
pipeline doit tourner régulièrement sur un cluster déjà en place — pas avant.
