J'ai vu un pipeline CI/CD "tout vert" déployer en production un modèle nettement moins bon que
celui qu'il remplaçait. Les tests unitaires passaient, le build passait, tout passait — sauf
que personne n'avait pensé à vérifier la performance du nouveau modèle par rapport à l'ancien.
C'est le trou que le CI/CD classique laisse ouvert sur un projet ML.

## Ce qui manque au CI/CD standard

Un pipeline logiciel classique répond à "le code compile, les tests passent". Un pipeline ML
doit en plus répondre à trois questions supplémentaires : les données d'entrée respectent-elles
le schéma attendu, le nouveau modèle est-il au moins aussi bon que celui en place, et le temps
d'inférence reste-t-il dans les clous de latence acceptés.

## Structure minimale

```yaml
# .github/workflows/ml-pipeline.yml
jobs:
  test-code:
    steps:
      - run: pytest tests/

  validate-data:
    needs: test-code
    steps:
      - run: python scripts/validate_schema.py

  train-and-evaluate:
    needs: validate-data
    steps:
      - run: python scripts/train.py
      - run: python scripts/evaluate.py --min-auc 0.75

  register-model:
    needs: train-and-evaluate
    if: github.ref == 'refs/heads/main'
    steps:
      - run: python scripts/register_model.py --stage Staging
```

`evaluate.py --min-auc 0.75` fait échouer le pipeline si le seuil n'est pas atteint, exactement
comme un test unitaire ferait échouer un build classique.

## Automatiser l'entraînement, pas forcément la mise en prod

Tant qu'une équipe n'a pas une confiance établie dans son pipeline, garder une validation
humaine avant de passer un modèle de `Staging` à `Production` reste une bonne idée — via une
pull request sur le Registry, ou une approbation explicite dans l'outil de CI. Automatiser
entièrement l'entraînement et l'évaluation, oui ; automatiser la décision finale, pas
immédiatement.

Un pipeline vert ne garantit rien sur la fiabilité du modèle si les seuils de validation n'ont
pas été revus depuis des mois — un modèle peut très bien dépasser un seuil devenu obsolète
parce que le jeu de test de référence, lui, n'a pas changé.
